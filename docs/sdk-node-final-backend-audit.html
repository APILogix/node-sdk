SDK Node Backend Readiness, Workflow, Features, Pros, Cons, and Defect Report

Static enterprise audit of the sdk-node backend SDK implementation as of 2026-05-24. This document is intended to be the final engineering-facing reference for current behavior, production strengths, blocking defects, and release readiness.

Package@vikasbaplawat1/pulse-sdk 2.0.0
Runtime TargetNode.js backend services, Fastify, Express, workers
Current VerdictScalable foundation, not enterprise-ready yet

Executive Summary

The SDK has a serious backend architecture: remote config concepts, feature gates, killswitches, OTel-based tracing, multi-route transport, persistent storage, security scrubbing, metrics, logging, and framework instrumentation. The implementation is beyond a hobby SDK and has the right major building blocks for production.

Release blocker: the current code should not be marketed as enterprise-grade until shutdown/reinit safety, remote config correctness, pre-init scrubbing, dynamic killswitch behavior, trace/log/metric correlation gaps, and transport config compliance are fixed and covered by tests.
Architecture Scalable concept, with remote control plane and modular subsystems.
Runtime Risk High under long-lived services, reinit, dynamic config, and high burst traffic.
Readiness Scalable, not production-grade

SDK Node Workflow

The backend SDK lifecycle is split into initialization, capture, processing, transport, persistence, and shutdown. The design is good, but several replay and shutdown paths bypass the same guarantees as the hot capture path.

1. init(options) Validates options, loads remote config, applies version policy, initializes feature gates, sampling, limits, scrubber, and transport.
2. Capture APIs captureError, captureMessage, captureMetric, request hooks, logging, and auto instrumentation create SDK events or OTel telemetry.
3. Event Pipeline Normalizes events, enforces limits, scrubs sensitive data, enriches context, deduplicates, runs plugins/processors, and applies beforeSend.
4. Transport Router Classifies telemetry by route, queues by type, batches, applies route health, sends to configured ingestion endpoints, and persists on failure.
5. OTel Tracing Creates an SDK tracer provider, span processor, exporter, context propagator, and framework instrumentations when tracing is enabled.
6. Metrics Public metric APIs route into an internal registry and OTel metric adapter, then emit metric events via a Pulse metric reader.
7. Persistence Offline or failed events are written as NDJSON in local cache/temp storage and replayed on future initialization.
8. shutdown() Flushes tracers, metrics, event pipeline, transport queues, plugins, handlers, deduplicator, storage, and client state.

Hot Path Flow

capture API or instrumentation -> enqueueEvent() -> async processEventAsync() -> limits and sampling gates -> normalize event -> security scrubber -> context enrichment -> deduplication and scope enrichment -> source map resolution -> plugin processors and event processors -> beforeSend -> TransportRouter.send() -> route queue -> BatchManager -> fetch ingestion endpoint -> persist or drop on failure

Feature Inventory

The SDK contains many production-grade concepts, but not every exposed feature is complete. Treat the table below as the current source of truth for implementation status.

Version policy Implemented Blocks, force-upgrades, or degrades SDK behavior during init.

Where The SDK Stands Out

Production Strengths

  • Uses OpenTelemetry primitives for trace IDs, span IDs, context propagation, and exporters instead of a fully custom tracing stack.
  • Has a remote-control-plane architecture: version policy, feature gates, killswitches, sampling, limits, transport routes, and security rules.
  • Contains a real event pipeline with normalization, scrubbing, enrichment, deduplication, processors, plugins, and beforeSend.
  • Transport separates telemetry by route and gives errors/crons higher priority than bulk metrics and traces.
  • Persistent storage gives offline survivability and crash-replay intent.
  • Security scrubber and sanitizer modules show awareness of PII, headers, and payload redaction.
  • Unit suite has meaningful coverage for core control-plane modules. Earlier local run passed 98/98 unit tests.

Important Limitations

  • Several features are configured or advertised before they are complete across runtime paths.
  • Replay paths do not consistently pass through the same sanitization and processor guarantees as live events.
  • Shutdown and reinit behavior is not clean enough for long-lived services, tests, serverless warm starts, or dynamic reload systems.
  • OpenTelemetry compatibility is promising but not complete enough for enterprise distributed tracing claims.
  • Remote config is central to the design, but some returned transport settings are ignored.

Critical Bugs

These are release-blocking or high-severity defects. P0 means data privacy, production correctness, lifecycle safety, or enterprise reliability can fail. P1 means serious behavior is wrong under common production conditions.

Severity Area Bug Impact Enterprise Fix
P0 Remote config ConfigManager.initialize() only builds configUrl from options.configUrl or options.baseUrl. It does not fall back to the resolved default/env base URL used by legacy init. Normal env-based deployments can silently skip remote config and run baked-in defaults while legacy /v1/init still succeeds. This breaks killswitches, sampling, limits, endpoints, and version policy expectations. Resolve base URL once in init and pass it into ConfigManager. Add tests for SDK_BASE_URL, default base URL, explicit baseUrl, and explicit configUrl.
P0 Privacy and pipeline consistency Pre-init buffered events and persisted replay events are sent directly via transportRouter.send() instead of the full event pipeline. Events captured before init can bypass security scrubber, enrichment, plugin processors, event processors, beforeSend, final limits, and normalization. This is a privacy and compliance risk. Create a replay-safe pipeline mode that executes scrubber, limits, processors, and beforeSend exactly once before transport. Add regression tests with sensitive headers captured before init.
P0 Shutdown and reinit shutdown() does not destroy ConfigManager, does not reset signal handlers, and does not reset auto instrumentation. Config refresh timers/listeners can survive shutdown. Reinit can miss signal handlers or keep stale global patches. This causes leaks, duplicated work, and broken behavior in tests, serverless warm starts, and hot reloads. Call ConfigManager.destroyInstance(), resetSignalHandlers(), auto instrumentation teardown/reset, and subsystem teardown inside shutdown. Add shutdown/reinit tests.
P0 Killswitches Tracing and metrics killswitch shutdown callbacks only log. They do not call shutdownTracer(), disable instrumentation, or stop metric readers. A backend-triggered emergency killswitch does not actually stop telemetry collection for active tracing/metrics. This violates remote control-plane guarantees. Make killswitch callbacks idempotently stop/start real providers, metric readers, processors, and instrumentation patches. Verify with dynamic config-change tests.
P0 OpenTelemetry lifecycle Tracer reinit can bind to existing global OTel state after provider shutdown. shutdownTracer() removes the SDK symbol but cannot reset global OTel registration. After shutdown/reinit, spans can be created against a dead or external provider. In multi-SDK or test environments this causes missing traces and hard-to-debug exporter failures. Do not claim ownership of existing globals. Track owned provider explicitly, avoid reusing shutdown providers, document coexistence behavior, and test init/shutdown/init span export.
P1 Transport config TransportRouter hard-codes queue, batch, timeout, compression, payload, and connection settings instead of honoring remote transport endpoint config. Backend cannot tune high-RPS deployments. Compression and timeout policy can be wrong. Enterprise control-plane claims are weaker than the code. Map every remote transport setting into BatchManager, TransportEventQueue, and ConnectionManager. Reject invalid backend config at initialization.
P1 Transport routing RouteRegistry.forcePath() overwrites configured endpoint paths to fixed /v1/* paths. Custom backend routes, tenant-specific paths, proxies, regional ingestion, and canary endpoints can be silently ignored. Respect full configured endpoint URLs. If path normalization is required, make it explicit and server-driven.
P1 Persistent storage Rotated .bak persistence files are not replayed or cleaned. Rotation can move pending events out of the only replay path. Offline backlogs can be lost after rotation, and disk can grow with stale backup files under sustained outage. Replay all segment files in order, compact acknowledged events, enforce total directory size, and delete expired segments.
P1 Error sampling captureError() samples before full fingerprinting and uses message-level sampling identity. Different tenants, routes, releases, or stack roots with the same message can be suppressed incorrectly before enterprise deduplication has enough context. Normalize and fingerprint first, then sample using service, environment, release, tenant, route, error class, and fingerprint.
P1 Trace quality Cost governor can drop spans at export time. Partial traces and orphan child spans can reach ingestion, making parent-child trees misleading under high span volume. Make sampling/drop decisions at span start, or mark dropped span counts on parent/root. Never silently export broken trace trees.
P1 Metrics correlation MetricEvent generation does not attach active traceId and spanId. Metrics cannot be reliably linked to the request/span that emitted them. This weakens debugging for latency, errors, and saturation. Add optional exemplar/correlation fields with cardinality controls. Do not label metrics with raw trace IDs; store linkage as exemplar metadata or event metadata.
P1 Public integration Fastify helper exists but is not exported from the root public API. Users cannot easily install the SDK Fastify plugin from the documented package root. This leads to inconsistent manual integration. Export Fastify instrumentation from src/index.ts and document registration order and encapsulation behavior.

Other Bugs And Gaps

High Severity

  • Shutdown sets eventQueue.setShuttingDown(true) only after tracer/metrics flush and event pipeline drain. New events can still enqueue during early shutdown.
  • Auto instrumentation has a global guard and axios cleanup list, but shutdown does not call teardown. Global monkey patches can outlive SDK lifecycle.
  • Retry behavior can requeue server failures without a per-event max retry or dead-letter budget, creating retry storms during long ingestion outages.
  • Compression config exists but payloads are sent as raw JSON in BatchManager. Backend and SDK can disagree about expected encoding.
  • Axios manual spans can duplicate spans already produced by OTel HTTP instrumentation.
  • Worker-thread propagation serializes context but no public worker-side restore path is wired into a complete workflow.
  • Baggage and B3 config appear in the type/config surface but distributed propagation implementation is W3C-focused and not fully wired to those options.

Medium Severity

  • Metric cardinality limit option is accepted but the cardinality governor uses fixed defaults instead of the remote/user limit.
  • Histogram unit is accepted through public API layers but is not preserved consistently into OTel metric recording.
  • Express error middleware flow is incomplete: next(err) is not automatically captured as a first-class SDK error event.
  • Console error capture and logging subsystem can both wrap console methods, creating duplicate events or ordering surprises.
  • Some advertised features such as session replay, AI detection, runtime metrics, GC monitoring, and release tracking are partially implemented or config-only.
  • Persistent storage eventCount is a lifetime counter except after discard/rotation. It can rotate based on writes rather than actual file contents.

Low Severity

  • Some comments and documentation blocks contain encoding artifacts, which makes generated docs less professional.
  • Remote config fetch timeout timer in the initial promise race is not cleared when fetch wins, creating minor transient timer retention.
  • Internal route names and public feature names are not always aligned, increasing support/debug complexity.
  • Fallback behavior is often fail-open. This is useful for app safety, but enterprise users also need explicit degraded-mode telemetry.

Capability Status Audit Result

Parent-child span relationships At risk OTel parentage is correct for normal context paths, but export-time span dropping and duplicate axios/http spans can create misleading trees.

Error Correlation

  • Errors can include active trace/span context when captured inside active OTel context.
  • Fingerprinting and source-map-aware grouping are strong concepts.
  • Sampling before robust fingerprinting is the primary correctness flaw.
  • Console, global error, framework, and manual capture paths need dedup tests to prevent duplicate issue creation.

Log Correlation

  • Log capture can attach current trace/span IDs through tracing helpers.
  • Concurrent request mixing risk remains if user scope mutation uses global scope rather than request-local context.
  • Child logger behavior and console monkey-patch layering need tests under concurrent requests.

Metric Correlation

  • Metrics are intentionally aggregated, so raw trace IDs should not be labels.
  • The SDK should support exemplars or event metadata for trace linkage instead of high-cardinality labels.
  • Current metric events do not provide enough request/span linkage for production incident debugging.

Transport And Reliability Audit

The transport layer is one of the strongest architectural areas, but it currently underuses its own remote configuration model.

Pros

  • Separate error, trace, metric, log, profile, and cron routes.
  • Bounded in-memory queues reduce unlimited memory growth.
  • Route health monitor and circuit behavior exist.
  • Shared connection manager models global and per-route concurrency.
  • Persistence fallback gives outage resilience.

Cons

  • Backend-supplied batch sizes and timeouts are not applied.
  • Compression policy is not honored.
  • Endpoint paths are forced rather than respected.
  • Retry policy lacks per-event max attempts.
  • Rotated persistence segments are not replayed.
Production implication: under a 10k concurrent request burst with backend ingestion degraded, the SDK will avoid unbounded memory because queues are capped, but it can produce dropped telemetry, retry churn, stale persistence segments, and behavior that cannot be tuned remotely.

Security And Privacy Audit

The SDK has strong security intent. The main issue is not the scrubber design; it is inconsistent routing around the scrubber on replay and early capture paths.

Area Good Risk Required Fix
Header scrubbing Framework integrations sanitize common sensitive headers. Ad hoc sanitization must not be the only protection. Central scrubber must run on every event path, including pre-init and replay.
Payload scrubbing Security scrubber and API payload sanitizer exist. Events sent directly to transport bypass user processors and scrubbers. Route all events through one processing contract before transport.
Persistent storage Storage is local and API-key namespaced by hash suffix. Sensitive events can be written if captured before scrubber initialization. Buffer only minimal safe envelopes pre-init, or scrub synchronously before buffering.
Tenant isolation Dedup pipeline can include tenant/route. Early error sampling does not include tenant/route. Sample on enterprise fingerprint after context enrichment.

Performance And Memory Audit

What should scale

  • OTel context avoids custom async_hooks maps and reduces risk of homegrown context leaks.
  • Bounded queues prevent unlimited in-memory backlog during ingestion outages.
  • Batching reduces request-per-event overhead.
  • Priority routing protects error/cron events from being treated the same as bulk traces/metrics.

What can fail at load

  • High-cardinality metrics can still be created because cardinality limits are not fully wired to user/remote config.
  • Retry loops can repeatedly requeue batches during prolonged 5xx/429 outages.
  • Export-time span dropping can create broken traces exactly when traffic is high.
  • Console/log capture can generate additional telemetry volume on already hot paths.
  • Persistent storage rotation can accumulate backup files during outages.
  • Shutdown can accept new events during early flush phases, increasing tail loss risk.
Load-test expectation: the SDK should survive high RPS better than a naive SDK because queues are capped and batching exists. However, correctness under 10k concurrent requests is not proven until trace isolation, scope isolation, retry budget, dynamic config, and shutdown/reinit tests are added.

Testing Posture

The existing unit suite is valuable, but it mostly validates modules in isolation. Enterprise readiness requires lifecycle, concurrency, and integration tests that intentionally break async and transport assumptions.

Current Positives

  • Earlier local run of npm run test:unit in sdk-node passed 98/98 tests.
  • Tests cover many control-plane modules such as feature controller, killswitch engine, limits, sampling, security scrubber, and transport units.
  • The codebase is TypeScript-first and structured for targeted unit tests.

Missing Release Gates

  • Concurrent request trace isolation test with Fastify and Express.
  • Shutdown, reinit, shutdown, reinit lifecycle test with real spans and metrics.
  • Pre-init privacy test proving sensitive headers are scrubbed before transport or disk.
  • Remote config env/default URL test.
  • Transport remote-config compliance test for batch size, timeout, compression, and endpoint path.
  • Persistent storage rotation/replay/cleanup test.
  • Worker-thread propagation restore test.
  • OpenTelemetry interoperability test with an existing global provider.

Remediation Roadmap

P0 Before Production Claim

  • Fix ConfigManager base URL/default/env resolution.
  • Route pre-init and persisted replay through the same scrubber and processor contract.
  • Implement full shutdown cleanup for ConfigManager, signal handlers, instrumentation, tracing, metrics, and logging.
  • Make dynamic tracing/metrics killswitches actually stop active providers.
  • Add init/shutdown/reinit and privacy regression tests.

P1 For Production-Grade

  • Honor all remote transport settings.
  • Fix persistence rotation replay and cleanup.
  • Move error sampling after full fingerprint/context enrichment.
  • Prevent export-time orphan spans.
  • Add metric exemplars or safe trace linkage.
  • Export and document Fastify integration.

P2 For Enterprise-Grade

  • Complete baggage, B3, and worker-thread propagation workflows.
  • Add high-RPS load tests and memory regression budgets.
  • Document exact feature support versus roadmap features.
  • Add compatibility tests with existing OTel providers.
  • Add golden telemetry snapshots for every event type.

Final Verdict

Enterprise readiness score: Scalable. The SDK is not a hobby implementation. It has a real architecture and several production-oriented controls. It is also not yet production-grade or enterprise-grade because important lifecycle, privacy, dynamic control, distributed tracing, and transport-config paths are incomplete or inconsistent.

The shortest honest positioning is: strong scalable foundation, production beta after P0 fixes, production-grade after P1 fixes and load tests, enterprise-grade only after propagation, reinit, remote-control, and compliance tests are enforced in CI.
