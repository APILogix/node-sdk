SDK Initialization

Initialization Flow

Complete documentation of the SDK initialization process, from options validation to subsystem startup.

Initialization Flow Diagram

Step-by-Step Breakdown

Step 1: Options Validation ▼

The SDK validates user-provided options using a Zod schema:

import { sdkInitOptionsSchema } from './types/config.js'

function validateInitOptions(options: SDKInitOptions): void {
  const result = sdkInitOptionsSchema.safeParse(options)
  if (!result.success) {
    throw new SDKError(`Invalid SDK init options: ${issues.join('; ')}`, 'INVALID_INIT_OPTIONS')
  }
}

Validation includes: API key format, service name, environment, sample rate bounds (0-1), transport config validation.

Step 2: Remote Config Fetch ▼

The SDK calls the backend /v1/init endpoint to get project-specific configuration:

const response = await sendInitRequest(
  options.apiKey,
  baseUrl,
  DEFAULT_TIMEOUT_MS,
)

Response includes: ingest URL, sampling rate, feature flags, plan tier, batch size, queue limits.

Retry Logic: The init request retries up to 5 times with exponential backoff (500ms-5s) for network errors and 5xx responses.
Step 3: Plan Features Resolution ▼

The SDK resolves plan features from the backend response, merging with tier defaults:

const planTier: PlanTier = remoteConfig.plan ?? 'free'
const planFeatures = resolvePlanFeatures(planTier, remoteConfig.planFeatures)

Plan tiers: Free Pro Enterprise

Step 4: Config Merging ▼

User options are merged with remote config, with all features defaulting to ON:

const rawConfig = mergeConfig(options, remoteConfig, planFeatures)
// Result: { enableErrors: true, enablePerformance: true, ... }
Step 5: Plan Clamping ▼

The raw config is clamped to plan limits - features above plan are forced OFF:

const resolvedConfig = clampToPlan(rawConfig, planFeatures)
// Free plan: enablePerformance: false, enableTracing: false, etc.
User Override: Users can disable features but cannot enable features above their plan tier.
Step 6: Plugin Initialization ▼

Plugins are registered and their setup() hooks are called:

for (const plugin of plugins) {
  client.registerPlugin(plugin)
  await plugin.setup(context) // context has config, metadata
}

Plugin count is capped by plan (Free: 0, Pro: 3, Enterprise: unlimited).

Step 7: Subsystem Startup ▼

Core subsystems are initialized:

  • Batcher: Starts the flush timer for batched event sending
  • Global Error Handlers: Registers uncaughtException and unhandledRejection handlers
  • Signal Handlers: Registers SIGTERM/SIGINT for graceful shutdown
  • Error Deduplicator: Starts the cleanup timer for fingerprint tracking
  • Metrics Registry: Starts the flush interval for aggregated metrics
  • Tracer: Initializes OpenTelemetry if enabled
  • Session Manager: Creates the session tracking instance
  • Resource Detector: Collects host/container/cloud metadata

Pre-init Buffering

Events captured before SDK initialization are automatically buffered and processed once the SDK is ready:

if (!client.initialized) {
  eventQueue.add(event) // Buffer without processing
  return true
}

This ensures no telemetry is lost during startup.

Offline Fallback

If the backend is unreachable after all retries, the SDK initializes with offline fallback config:

  • Errors: enabled (critical)
  • Performance: disabled
  • Queue size: 100 (Free tier limit)
  • Sampling: 1.0 (send all errors)
Warning: Offline fallback uses basic functionality. Consider implementing health checks for production deployments.
