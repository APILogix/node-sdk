Pulse SDK — Internal Engineering Guide

Audience: internal engineers working on the SDK itself. Every claim here is derived from reading the full source tree; see the repository audit. Proprietary backend endpoints and infrastructure topology are described structurally, not reproduced literally. For the customer-facing equivalent, see SDK Docs.

1. Architecture Overview#

The SDK is built around one idea: the backend is the sole source of runtime policy. A validated, immutable configuration snapshot is fetched exactly once at boot, and every subsystem — sampling, killswitches, entitlements, limits, transport routing, privacy scrubbing, instrumentation selection — reads from that one frozen object. The snapshot can later be atomically replaced (never merged) by a second, event-driven refresh.

mermaid
ConfigManager (immutable snapshot owner)
  |
  +--> KillswitchEngine        +--> SamplingEngine
  +--> FeatureController       +--> LimitsEngine
  +--> EntitlementGate         +--> SecurityScrubber
  +--> TransportRouter (10 per-event-type routes)
  +--> OTel TracerProvider -> PipelineSpanExporter -> event pipeline
  +--> OTel MeterProvider -> PulseMetricReader -> event pipeline
  +--> LoggingSubsystem / ProfilingSubsystem / CronSubsystem / SessionManager

Every engine follows the same lifecycle contract: initialize() / getInstance() / handleConfigChange(diff, config) / reset(). This uniformity is what makes shutdown-and-reinit tractable.

2. SDK Boot Sequence#

createSDK() wraps init(). Boot performs exactly one network operation: a single POST to the control plane, with the API key sent via an HTTP header (not the JSON body). The response is validated by a hand-written structural validator, hashed, and deep-frozen. Only after every engine singleton is constructed and the transport router is built does client.markInitialized() run — before that point, capture calls are buffered in a bounded pre-init queue rather than dropped.

Full 18-step sequence with a Mermaid diagram is in docs/internal-sdk.md §2.

3. Complete Event Lifecycle#

All ten SDKEvent shapes converge on one function: enqueueEvent(). Synchronous gates (shutdown state, killswitch, load shedder, pre-init buffering, in-flight cap) run first and can reject cheaply before any async work is scheduled. Once accepted, exactly one setImmediate() defers the async pipeline: feature gate, entitlement gate, sampling, tenant admission, attribute limits, normalization, context enrichment, error deduplication, scope merge, source-context attachment, plugin/processor/beforeSend hooks (each individually timeout-bounded), and finally routing to the transport layer. SDK-owned identity metadata is force-reassigned after every hook runs, so no hook can forge project/application identity.

4. Batching Architecture#

Each of the 10 event-type routes owns its own bounded queue and BatchManager. A batch flushes at maxBatchSize or maxWaitTimeMs, whichever comes first. Minimum batch sizes are hardcoded per route: errors/crons/profiles/replays/events=1 (near-immediate flush), traces/spans/requests/logs=10, metrics=50. Oversized batches are split in half recursively until they fit or a single event is dropped. The wire body is always gzip-compressed on the primary send path regardless of the configured per-route compression value.

5. Sampling#

All sampling is deterministic: an FNV-1a 32-bit hash of a stable identifier, normalized to [0,1) and compared against a configured rate. There is no Math.random() anywhere in the sampling path. Trace-level sampling happens once at root-span creation via a custom OTel sampler wrapped in a ParentBasedSampler; child spans inherit the decision. A tail-based promotion keeps unsampled spans that carry an error status, so error-bearing traces are never silently dropped by sampling alone.

6. Remote Configuration#

There is no polling anywhere in the codebase. A refresh happens only after a telemetry acknowledgment explicitly signals a change (HTTP 202 plus a change: true field in the response body). The new snapshot either replaces the entire previous one atomically or is ignored (older by timestamp, or byte-identical by content hash) — there is no merge strategy.

7. Retry Architecture#

Retry-eligible failures are network errors and HTTP 5xx/429/408; any other 4xx is a permanent rejection that is dropped, not persisted. Backoff is exponential, linear, or fixed depending on remote config — with no jitter, a confirmed gap noted in the repository audit. Persistence to disk is fallback-only: it happens only on an actual send failure or a shutdown-time drain timeout, specifically to avoid replaying already-delivered events on every restart.

8. Auto Instrumentation#

A single entitlement check (tracing) multiplies across almost every instrumentation flag — if revoked, every automatic instrumentation is disabled regardless of its individual remote config value. HTTP/Undici instrumentation self-excludes the SDK's own telemetry traffic by comparing target URLs against every configured route URL. Redis always redacts a hardcoded list of sensitive commands regardless of capture settings. Full per-integration table (library, patch mechanism, captured data, limitations) is in docs/internal-sdk.md §8.

9. Context Propagation#

Two channels run side by side: OpenTelemetry's own AsyncLocalStorage-backed context (owns trace/span identity) and the SDK's own ContextStore (request ID, breadcrumbs, user/session, tags). Worker threads intentionally do not get their own OTel provider — a serialization module exists for passing a correlation snapshot into workerData, but it currently has no export path from either public entry point.

10. Shutdown#

shutdown() is single-flight and races its real cleanup against a timeout; if the deadline wins, cleanup keeps running in the background and a subsequent init() waits for it. An unconditional cleanup phase always runs regardless of orchestrated-phase success, null-resetting every singleton so reinit is genuinely clean. crashFlush() is the lightweight crash-path variant, skipping subsystem and plugin teardown entirely.

11. Performance#

Concrete, code-verified numbers: one setImmediate() per accepted event; 50ms budget for plugin/processor hooks, 100ms for beforeSend; 250ms total budget for source-context attachment. Histogram recording is O(1) via OTel exponential-histogram aggregation, a deliberate move away from an earlier sort-based design that had a documented percentile-accuracy bug. No independent load-test numbers exist in this repository.

12. Edge Cases#

Double initialization, invalid API keys, network unavailability at boot and steady-state, queue/batch overflow, process crashes, flush timeouts, transport unavailability, remote config unavailability, disabled sampling, instrumentation conflicts, circular references, huge payloads, memory pressure, and recursive logging are each handled by specific, traceable mechanisms — not left undefined. Full list in docs/internal-sdk.md §12.

13. Design Decisions#

Immutable-snapshot-no-merge, fallback-only persistence, deterministic sampling, direct-to-stream internal logging (to break a real observed console-interception feedback loop), separated features/killswitches/entitlements axes, and OTel-native metrics (replacing a sort-based design with a documented percentile bug) are each explained with their tradeoffs in docs/internal-sdk.md §13.

14. Future Improvements#

Observed opportunities, not commitments: add retry jitter; reconcile the currently-inert transport.routes.*.compression field; implement or remove heap profiling and B3 propagation from the type system; provide an export path for the worker-context module or remove it; compute MetricEvent.rate from real throughput instead of always zero.
