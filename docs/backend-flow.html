Pulse SDK v3 — Backend Control Flow

How the SDK and the control plane cooperate. Every behaviour the SDK has at runtime — what it captures, where it sends it, when to drop, when to back off — is sourced from one remote-config response. The SDK itself ships only safe defaults and hard ceilings.

1. The big picture

The SDK and the backend talk over three logical endpoints. One ships config, one ships events, and one is reserved for control-plane health signals. Everything the customer's running app does observably is the product of these three streams.

1
App calls init({ apiKey })
SDK boots in safe-defaults mode (transport off, sampling 0). Non-blocking.
2
POST /v1/sdk-config
SDK fetches its config. 3-second timeout. On failure: keep safe defaults, retry every 30s in the background.
3
Schema-version gate + safety clamping
Reject configs newer than SDK understands. Clamp every numeric field to SAFETY_CEILINGS.
4
Engines wired up
Sampling, killswitches, limits, scrubber, transport router, feature controller — all driven by the same config snapshot.
5
Background refresh loop
Every runtime.configTtlSeconds the SDK refetches. Diff is computed. Subsystems hot-swap.
6
Events flow to per-event-type routes
traces → /v1/traces, errors → /v1/errors, requests → /v1/requests, etc. Each with its own batch size, flush interval, retry policy.

2. Bootstrap sequence

This is what happens in the first 3 seconds after init(). The SDK is non-blocking the entire time — your app keeps serving traffic no matter what the control plane is doing.

t = 0ms
App calls init() / createSDK().

SDK loads BAKED_IN_REMOTE_CONFIG — every feature off, transport disabled, sampling 0. The app's request handlers are now wrapped, but every captured event is dropped silently. This is intentional: it gives the SDK a window to talk to the backend without losing or sending bad data.

t = ~50ms
Config fetch issued.

SDK builds the request body — its identity (sdkVersion, service, environment, runtime) plus a list of capabilities the binary supports — and POSTs to ${baseUrl}/v1/sdk-config.

POST /v1/sdk-config
Authorization: Bearer pk_live_...
Content-Type: application/json

{
  "sdkVersion": "3.0.0",
  "sdkName": "@vikasbaplawat1/pulse-sdk",
  "service": "payments-service",
  "environment": "production",
  "runtime": "node",
  "runtimeVersion": "v20.11.0",
  "capabilities": [
    "tracing", "requestCapture", "errors", "metrics",
    "logging", "profiling", "crons",
    "runtimeMetrics", "eventLoopMonitoring", "gcMonitoring"
  ]
}
t = ~150ms
Backend responds.

The control plane looks up the project, applies billing / plan / org rules backend-side, and returns the resolved config. The SDK never sees plan tiers, billing flags, or any of the upstream business logic.

t = ~150ms
Schema gate.

If schemaVersion > 1: reject. SDK keeps safe defaults and logs "SDK upgrade required". This means your fleet can never break from a forward-incompatible backend release.

t = ~155ms
Merge: baked-in → remote → user init opts.

Remote config wins over baked-in. User init() options win over remote (only for the few client-side overrides like sampleRate).

t = ~156ms
Safety clamping.

Every numeric field is clamped to SAFETY_CEILINGS. A backend mistake like "maxQueueSize": 1_000_000_000 is silently coerced to 100_000. Floors apply too: flushIntervalMs < 100ms is bumped up to prevent self-DoS.

t = ~160ms
Engines initialise.

KillswitchEngine reads killswitches.*, SamplingEngine reads sampling.*, LimitsEngine reads limits.*, SecurityScrubber reads privacy.*, TransportRouter reads transport.routes.*, FeatureController reads features.*.

t = ~165ms
Subsystems start.

FeatureController walks its registry; for every feature whose remote flag is true, the corresponding subsystem (logging interceptor, profiler, cron checker, ...) is instantiated. Features whose flag is false are never instantiated — zero CPU/memory overhead for unused features.

t = ~170ms
Background refresh loop armed.

A setInterval with { unref: true } fires every runtime.configTtlSeconds. The SDK never pins the event loop alive on its own.

t = ~175ms
Pre-init buffer drained.

Any events captured during the bootstrap window were buffered. They're now flushed through the live pipeline.

What if the backend is unreachable? The SDK keeps running on baked-in defaults (transport off, sampling 0, all features off). It retries the fetch every 30 seconds in the background. As soon as a real config arrives, every subsystem flips on at once. The host application is never blocked or impaired.

4. The capture pipeline

Every event — error, request, span, metric, log — flows through the same pipeline. Each gate either drops the event with a reason or hands it to the next step. None of the gates can crash the host.

Gate Killswitch: disableSDK → drop everything. disableTracing → drop spans + requests. disableErrors → drop errors. Etc.
Gate FeatureController: features.requestCapture = false → request events dropped before any work.
Gate TenantGovernor: per-tenant sliding window. Tenant X is over quota → drop until window resets.
Gate SamplingEngine: deterministic FNV-1a hash of traceId. Per-route override map: routes["/health"] = { requests: 0 } → drop.
Gate Memory pressure: heap > 92% → drop low-priority telemetry. Errors and root spans still survive.
Gate LoadShedder: adaptive shedding under sustained pressure.
Step Normalize: fill defaults, truncate oversized fields per limits.maxAttributeLength.
Step SecurityScrubber: redact privacy.scrubbing.headers + privacy.scrubbing.fields. Mask emails / phones / IPs per privacy.piiDetection.
Step Enrich: attach traceId, spanId, breadcrumbs, scope (user, tags, extra, contexts).
Step LimitsEngine: trim attributes to limits.maxSpanAttributes. Truncate long strings.
Step Plugin / user processors: per-event-type hooks. beforeSend last; returns null → drop.
Exit TransportRouter: route by event type → batch in queue for the corresponding URL. Errors get their own queue, traces theirs, requests theirs.

6. Hot reload — config changes mid-flight

The control plane can change anything at any time. The SDK reacts within one refresh cycle (default 5 minutes; the backend can lower this for an on-call).

Backend changesSDK reaction
sampling.routes["/health"] = { traces: 0, requests: 0 } SamplingEngine picks up the new route map. Next event from /health is dropped at the gate.
features.profiling: true → false FeatureController calls the profiling subsystem's teardown — inspector disconnects, in-flight profiles flushed.
killswitches.disableTransport: false → true TransportRouter.disable(). Events keep entering the queue but nothing leaves. When the killswitch flips back, queued events drain.
privacy.scrubbing.fields += ["correlation_id"] SecurityScrubber recompiles its lowercased Set. Next event's correlation_id is redacted.
limits.maxQueueSize: 10_000 → 50_000 LimitsEngine updates. The queue itself doesn't shrink; new admissions can grow it up to the new ceiling.
transport.routes.errors.batchSize: 10 → 50 Next batch flushes with 50 errors instead of 10.
Backend rolls a new schemaVersion = 2 release SDK rejects the config: "schema version 2 is newer than SDK-supported version 1; SDK upgrade required". Falls back to the last known-good config (or baked-in defaults).

7. Failure modes — what protects you

FailureSDK behaviour
Backend down at startup Use BAKED_IN_REMOTE_CONFIG (transport off, sampling 0). Retry every 30s. App never blocks.
Backend slow (> 3s) Initial fetch times out. Same as "backend down".
Backend returns 500 Logged, swallowed. staleWhileRevalidate: keep using the last known-good config.
Backend returns malformed JSON Same as 500.
Backend returns config with typo (maxQueueSize: 1e9) Clamped to SAFETY_CEILINGS.maxQueueSize = 100_000. Host process safe.
Backend returns schemaVersion: 2 Refused. SDK keeps current config. Logs upgrade-required message.
Ingest endpoint down RetryBudget + circuit breaker. Events queue until queue is full → drop_oldest per transport.queue.overflowStrategy.
SDK panicking / killswitch needed Backend sets killswitches.disableSDK: true. Within one refresh cycle every public method becomes a no-op.

9. Backend responsibilities

The control plane is responsible for everything the SDK no longer is:

  • Plan / billing logic — turn features off when a customer is on the free tier; raise rates when they upgrade.
  • Per-org overrides — Acme Corp wants 100% sampling on /payments but the rest of the world stays at 10%.
  • Incident response — flip killswitches.disableSDK: true for a misbehaving customer in seconds.
  • Schema evolution — add fields freely; bump schemaVersion only on incompatible changes.
  • Capability negotiation — read the SDK's capabilities array on every fetch; never send a flag the SDK doesn't claim to support.
  • Anomaly thresholds — backend computes p99 latency from raw spans; SDK does not.
  • Auth — verify the API key, look up the project, return a config tailored to that project. SDK trusts the response.

10. SDK responsibilities

  • Capture — instrument frameworks, capture errors / spans / requests / metrics / logs.
  • Enforce remote config — every behaviour-affecting decision goes through the engines that read the live config snapshot.
  • Apply safety bounds — clamp every numeric value the backend sends to a hard ceiling. Refuse incompatible schema versions.
  • Buffer + ship — per-event-type queues, batching, retries, compression.
  • Stay invisible — never crash the host. Never block. Always degrade gracefully.
What the SDK does NOT do: decide who's on which plan, decide what counts as a slow request, decide whether feature X is allowed for tenant Y, dedupe across nodes, compute aggregate percentiles, alert on anomalies. All of that is the backend's job.
